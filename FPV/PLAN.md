# FTOS — План продукту для FPV рем-бригад

> Статус: чернетка архітектури, без коду. Узгодити перед розробкою.
> Дата: 2026-06-10. Принцип: без води, тільки правда. Інструмент **підказує**, відповідальність за фінальну перевірку — на технікові.

---

## 1. Що це і чого це НЕ є

**Є:** офлайн-довідник техніка, який із симптома («немає відео») за кілька тапів доводить до ймовірної причини й конкретного кроку фіксу, спираючись на пінаут саме тієї плати, що в руках. Працює в полі без інтернету, з телефона й з ПК.

**НЕ є (свідомо, у v1):**
- не діагностує сам по даним з борта (немає під'єднання до FC по USB у браузері — це окрема велика тема, Web Serial);
- не розпізнає плату по фото (ШІ/CV — пізніше);
- не хмарний сервіс з акаунтами (opsec + бар'єр входу);
- не «весь спектр одразу» — спектр закриваємо модулями по черзі.

**Чому так:** «перекрити все одразу» = зробити погано все. Сильний продукт = одне ядро, доведене до ідеалу, і модулі навколо нього.

## 3. Повний спектр ремонту → модулі → пріоритет

```
ЕТАП РОБОТИ                          МОДУЛЬ FTOS                ПРІОРИТЕТ
1. Прийом (що скаржиться)        →   Вхід у діагностику        v1  (ядро)
2. Ідентифікація плати/компонента →  База плат (фото пізніше)   v1 база / v3 фото
3. Діагностика симптом→причина   →   ЯДРО: дерева діагностики   v1  ★
4. Ремонт (пайка/заміна/прошивка)→   Кроки фіксу + Карта пайки  v1 (пайка є)
5. Налаштування (firmware/CLI)   →   Модуль прошивок            v2
6. Тест + видача                 →   Чек-лист видачі            v2
7. Облік (журнал + запчастини)   →   Локальний журнал ремонту   v2
```

Карта пайки (`lib/engine.ts`, вже написана) **не викидається** — вона стає одним із кроків фіксу (коли причина = заміна компонента), а не окремим продуктом.

## 4. Ядро: модель даних діагностики (серце)

Кожен симптом = **дерево перевірок**. Вузол або веде до наступної перевірки, або до причини з фіксом.

```ts
interface DiagnosticFlow {
  id: string;                       // "no-video"
  symptom: string;                  // "Немає відео на VTX"
  applies_to: {                     // коли показувати цей симптом
    drone_class?: 'fpv' | 'wing';
    has?: ('vtx_digital' | 'vtx_analog' | 'gps')[];
  };
  entry_node: string;
  nodes: Record<string, CheckNode | CauseNode>;
  verified: { status: 'draft' | 'manual_checked' | 'field_tested' };
}

interface CheckNode {
  type: 'check';
  instruction: string;              // "Поміряй напругу на VTX VCC"
  method: 'visual' | 'multimeter' | 'configurator' | 'swap' | 'listen';
  expected?: string;                // "5V ±0.2"
  pad_ref?: { role: string };       // тягне конкретний пад з профілю плати
  image?: string;                   // опц. фото точки виміру
  outcomes: { label: string; next: string }[];  // "0 В"→node, "5 В"→node
}

interface CauseNode {
  type: 'cause';
  cause: string;                    // "Згорів BEC 5V"
  fix_steps: string[];              // покрокова дія
  fix_action?: 'rewire' | 'reflash' | 'replace' | 'resolder';
  confidence: 'likely' | 'possible';   // НІКОЛИ не "точно"
  source_url: string;               // звідки знання
  est_minutes?: number;
}
```

**Гарантія правди:** на кожному `CauseNode` обов'язкові `confidence` + `source_url`. UI завжди показує «ймовірно / можливо» і лінк на джерело. DRAFT-дерево UI підсвічує жовтим — як уже зроблено для плат.

**Моат:** `pad_ref` тягне конкретний пад із наявного профілю плати (`data/boards/*.json`). Тому діагностика + база пінаутів + карта пайки = один організм. Цього в існуючих інструментів нема.

## 6. Технічна архітектура

| Шар | Рішення | Чому |
|---|---|---|
| Фронт | Next.js (лишаємось на 14, далі 15) + TS | вже є, статичний білд |
| Офлайн | **PWA + service worker**, прекеш app-shell + усіх JSON | поле без інтернету |
| Дані-довідник | статичні JSON (`boards/`, `components/`, `flows/`) | версіонуються в git, легко звіряти |
| Локальні дані | **IndexedDB (Dexie)** — журнал ремонтів, чернетки | приватно, без хмари |
| Акаунти | **немає у v1** | бар'єр + opsec |
| Синхронізація | пізніше: експорт/імпорт JSON або P2P; не критично для v1 | спершу цінність, потім інфра |
| Деплой | Vercel (роздача) + «встанови як застосунок» (PWA) | нуль налаштувань |
| UI | mobile-first, великі тап-зони, fixed bottom-навігація | однією рукою біля паяльника |

**Опційно, окремий модуль (v3):** Web Serial API → читати дані з FC прямо в браузері (порти, версія BF, сенсори). Тільки desktop Chromium, тому окремо й пізніше.

## 7. Дисципліна контенту (головний ризик)

Вузьке місце — **не код, а зміст дерев**. Неправильна порада = спалена плата в когось у руках.

Правила (поширюємо наявну DRAFT-логіку на дерева):
1. Кожне дерево має `source_url` і `verified.status`.
2. `draft` — написано, не звірено → UI жовте попередження.
3. `manual_checked` — звірено з мануалом/BF-docs другою людиною.
4. `field_tested` — підтверджено реальним ремонтом.
5. Жоден `CauseNode` без `confidence` + `source`.

Розподіл праці: **я роблю рушій + каркас контенту + 1–2 еталонні дерева**; масове наповнення правдою — технік, що реально ремонтує.

## 8. Каталог симптомів (черга авторингу)

Топ-5 для v1 (покривають більшість звернень):
1. **Немає відео** (VTX power → UART/SmartAudio → антена)
2. **Немає лінку з пультом / не біндиться** (RX power → протокол/UART → ребайнд)
3. **Не армиться** (arming flags у BF → акселерометр/кути → failsafe/throttle)
4. **Мотор не крутить / крутить не туди** (ESC сигнал → пайка → motor order/direction)
5. **Плата не конектиться до конфігуратора** (USB/драйвер → bootloader/DFU → коротке)

Наступна хвиля (v2): немає GPS-фіксу · дрифт/тоффи · перегрів · OSD пустий · немає телеметрії · просідає живлення.

## 9. Роадмап по майлстоунах

**M1 — Ядро (вертикальний зріз):**
- модель даних + рушій обходу дерева;
- екран «обери борт → симптом → крокуй деревом → отримай фікс»;
- 1 еталонне дерево («немає відео»), звірене;
- PWA-офлайн шар.
→ *Результат: працює, уже корисно бригаді.*

**M2 — Покриття + ремонт:**
- решта 4 дерев топ-5;
- інтеграція `fix_action: rewire/replace` → наявна карта пайки;
- журнал ремонту (IndexedDB), запчастини;
- розширення бази плат (→15 із README).

**M3 — Налаштування + поле:**
- модуль прошивок (BF/INAV targets, CLI-пресети);
- чек-лист тесту/видачі;
- ідентифікація плати по фото або по характерних маркуваннях;
- (опц.) Web Serial читання з FC на ПК.

## 10. Ризики й мітигація

| Ризик | Мітигація |
|---|---|
| Неправильний контент → спалена плата | DRAFT-дисципліна + `confidence`/`source` на всьому; верифікація техніком |
| Scope creep («весь спектр») | строга черга M1→M2→M3; усе поза чергою — у backlog |
| Плат тисячі, ревізії різні | починаємо з найпоширеніших; «ревізія = окремий файл» (вже правило) |
| Офлайн на iOS обмежений | PWA-прекеш статики покриває 95%; журнал локально через IndexedDB |
| Контент застаріває (BF оновлюється) | `source_url` + дата звірки в кожному файлі |
